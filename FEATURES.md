# Новые возможности Tabby

В этом документе описаны функциональные изменения и нововведения, добавленные в приложение.
Материал подготовлен для коммита описывающий расширение функциональности Tabby.

---

## 1. Saved Credentials — пул сохранённых учётных данных SSH

### Что добавлено
Добавлена подсистема «Saved Credentials»: возможность один раз завести учётную запись
(логин, пароль, приватные ключи) и переиспользовать её в разных SSH-профилях и группах
профилей, не дублируя данные в каждом профиле вручную.

Конкретный функционал:
- **Управление пулом учёток** (Settings → SSH → секция «Saved credentials»):
  создание, редактирование и удаление сохранённых учётных данных.
- **Редактор учётки** (модальное окно): поля `Name` (понятное название строки),
  `Username`, список `Private keys` (добавление/удаление ссылок на файлы ключей через
  файловые провайдеры) и `Password` (установка/сброс, с индикатором сохранён/не задан).
- **Привязка учётки к профилю**: в редакторе SSH-профиля появилось поле
  «Use saved credential» (выпадающий список всех сохранённых учёток + вариант «None»).
  При выборе учётки в профиль автоматически подставляется `Username`, если он не задан.
- **Групповая учётка**: credential можно задать на уровне группы профилей (через group
  defaults). В этом случае все хосты группы подключаются под этой учётной записью, даже если
  у самих профилей credential явно не указан.
- **Безопасное хранение пароля**: пароль не сохраняется в конфигурации приложения. Он
  хранится в защищённом хранилище — встроенном Vault Tabby (при включённом vault) либо в
  системном связке ключей ОС через `keytar`. В конфиге от учётки хранятся только метаданные:
  `id`, `name`, `username` и список `privateKeys`.
- **Автоматическая подстановка при подключении**: при открытии SSH-сессии выбранная учётка
  «материализуется» — в профиль подставляются user, приватные ключи и пароль из хранилища,
  после чего происходит аутентификация.

### Обоснование
Ранее для каждого SSH-профиля учётные данные (логин/пароль/ключи) приходилось задавать
повторно и хранить непосредственно в самом профиле. При большом парке серверов это ведёт к
многократному дублированию одних и тех же данных, усложняет их ротацию (смена пароля = правка
во множестве профилей) и снижает безопасность (пароли лежат в конфиге профилей). Аналогичный
подход (единый пул учёток, привязываемый к хостам/группам) реализован в Termius и MobaXterm, и
пользователь ожидает такое же поведение.

### Польза
- **Устранение дублирования**: одна учётка переиспользуется во многих профилях и целых группах.
- **Упрощение администрирования**: смена пароля или ключа делается в одном месте (в учётке),
  а не в каждом профиле.
- **Безопасность**: секретный пароль не хранится в текстовом конфиге профиля, а лежит в
  защищённом хранилище ОС/vault.
- **Удобство**: выбор нужной учётки из выпадающего списка вместо ручного ввода данных;
  групповая привязка позволяет за один шаг «залогинить» целый парк серверов одной учёткой.

## 2. Улучшенный поиск по профилям и группам (Filter)

### Что добавлено
Переработано поведение строки фильтра («Filter») в двух местах интерфейса:
- боковая панель Connection Manager (дерево профилей);
- экран настроек Settings → Profiles.

Новое поведение:
- **Явный блок результатов**: при вводе запроса обычное дерево папок скрывается, а сверху
  выводится блок с заголовком `Found: N` (N — количество найденных сущностей). Результаты
  больше не «прячутся» внутри своих родных папок.
- **Плоский список профилей**: найденные профили показываются списком, причём рядом с каждым
  отображается имя его группы (контекст расположения).
- **Группы как раскрываемые результаты**: если запрос совпадает с именем группы, эта группа
  выводится как отдельный результат с возможностью раскрытия — при раскрытии видны её профили.
- **Поиск без учёта регистра**: запрос и все сравниваемые поля приводятся к нижнему регистру,
  поэтому поиск по имени, IP/хосту, пользователю, порту, jump host и имени группы работает
  независимо от регистра ввода.
- **Расширенный охват**: помимо имени профиля, поиск теперь учитывает хост (IP/адрес),
  пользователя, порт, jump host и имя группы, а не только название профиля.

### Обоснование
Исходный фильтр искал только по имени профиля и при совпадении оставлял результат внутри
дерева папок — пользователю приходилось раскрывать нужную папку, чтобы увидеть найденный
сервер. В реальной эксплуатации (сотни хостов в десятках групп) это неудобно: нужно быстро
найти сервер по IP или имени группы и сразу увидеть результат. Явный блок «Found» сверху и
поиск по техническим полям (хост/порт/юзер) напрямую отвечают сценариям администрирования.

### Польза
- **Скорость навигации**: результат поиска сразу виден вверху, без раскрытия дерева папок.
- **Гибкость поиска**: можно найти сервер по IP, по логину, по порту или по названию группы.
- **Удобство**: регистронезависимый поиск исключает ошибки «не нашлось» из-за Caps Lock или
  разного регистра в названиях.
- **Контекст**: рядом с найденным профилем показывается группа, что помогает понять, где
  находится хост, а найденная группа раскрывается для просмотра её содержимого.

## Итог
Добавлены две крупные пользовательские возможности:
1. **Пул сохранённых учётных данных SSH** с безопасным хранением паролей, привязкой к
   профилям и группам — для устранения дублирования данных и централизованного управления
   доступом.
2. **Улучшенный поиск** с явным блоком результатов «Found», регистронезависимым поиском и
   охватом технических полей (хост, порт, пользователь, группа) — для быстрой навигации по
   большому парку профилей.
